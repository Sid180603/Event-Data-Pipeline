# Handoff — Event Generator → Queue, Database, UI

**From:** the Event Generator team (slice 2). **To:** Queue (Kafka + Flink), Database
(Cassandra), UI.

This is the index of everything you need, and what each of you does with it. The binding document is
[`contracts/CONTRACT.md`](../contracts/CONTRACT.md) — if this file and the contract ever disagree,
**the contract is right** and this file is a bug.

**One honesty rule governs all of it: this project claims no throughput and publishes no
benchmark.** Every number below is either read out of a file in this repo or produced by a
measurement named in the same sentence. Where something could not be established from the code, it
says *"not established here"* rather than carrying a figure this project did not measure. Do not
inherit a number from this document that you cannot trace.

## 2. What each team is handed, and what each team owns

### UI — you send; we encrypt

**You must:** batch (≤ 200 events / ≤ 2 MiB), keep the connection alive, maintain `sequence`, reuse
`id` on retry, never send `*_enc` / `*_hmac` / `user_id_pseudo` and never rely on `partitionkey`.
The reasons are in contract §10; the obligations are unchanged. One detail worth having before you
write the SDK: sending `email_enc` is refused with **`SCHEMA at $.data.candidate`**, not with
`UNKNOWN_ATTRIBUTE` — that code is only for an unknown attribute at the *top level* of the envelope.

**You get:** four routes (§2 of the contract), the ingress schema, ten working examples, and a
`202 {accepted, rejected}` that reports per-event verdicts rather than failing the batch. A `202` is
**accepted into a bounded in-memory buffer**, not a durability receipt — retry a `503` with the same
`id`s.

**Two things we are handing you that are easy to get wrong:**

1. **The 48 KiB ingress cap is not a guarantee about the 64 KiB ceiling.** It was measured
   (`app/test_config.py`, real pipeline, real encryption; run it with `-s` to print the numbers):
   a 49,152 B event whose bulk is in `client_metadata` becomes 49,380 B and is published with 16,156 B
   of headroom, but the same size with the bulk spread across all five encrypted fields becomes
   **65,923 B — 387 B over the ceiling — and is refused**. The largest fully-encrypted event that fits
   is **48,855 B**, so **the top 297 B of the cap is admitted and then refused**: per event, with
   `OVERSIZED`, into the DLQ, while the rest of your batch is published normally. You will not see a
   `413` for this; you will see the event missing from the topic and named in the `202`'s `rejected`
   list. **Keep the five encrypted fields small.** This is open question 3 in §7 — a decision for you,
   not a settled fact. Full table in contract §2.
2. **`sequence` is your responsibility and it is the only thing that survives a restart.** There is no
   consistent-hash affinity layer in front of the uvicorn workers, so two events for one user can be
   produced by two different workers in an arbitrary order. Partition order is therefore not a
   contract; `sequence` is.

### Queue — one topic, the derived key, ordering by `sequence`, the DLQ

**You build on:** one topic `career.events.raw` (12 partitions, RF 1, `compression.type=zstd`,
6 h retention) and `career.events.dlq` (3 partitions, RF 1, 24 h). Both are created explicitly by
`kafka-init`; `auto.create.topics.enable` is off.

**The producer config that matters to you, inline** — you should not need to open the tuning doc for
any of these:

| Key | Value | Why it is your problem |
|---|---|---|
| `enable.idempotence` | `true` | **Forbidden to turn off.** With it off, retries duplicate and reorder with nothing raising. Covers the *producer's* retries — **not** a client's HTTP retry. |
| `acks` | `all` | RF 1 today, so it currently buys you the leader alone; it becomes load-bearing at RF > 1. |
| `retries` | `2147483647` | `INT32_MAX`; `message.timeout.ms` is what ends a produce. |
| `max.in.flight.requests.per.connection` | `5` | The largest value that still preserves order under idempotent retries. **Your ordering depends on this.** |
| `queuing.strategy` | `fifo` | Fixes hand-off order from the local queue. `lifo` would reorder within a partition while duplicating nothing — the worst kind of breakage, because nothing counts it. |
| `partitioner` | `consistent_random` | Hashes the key **we** supply. |
| `message.timeout.ms` | `5000` | A produce that fails is a record whose caller already holds a `202`. |
| `queue.buffering.max.kbytes` | `65536` (64 MiB) | librdkafka's own queue. Separate from the 50,000-record Python queue. |
| `linger.ms` / `batch.size` | `10` / `262144` | Coupled to the producer's poll interval. |
| `compression.type` / `compression.level` | `zstd` / `3` | Both topics are *created* with `compression.type=zstd`, so the client and the topic state the same intent. **Note the property name:** it is `compression.level`, not `compression.zstd.level` — the latter does not exist in librdkafka and `Producer()` raises `_INVALID_ARG` on it. |

`kafka_producer_config()` in `app/config.py` is the single source of truth for every one of these;
the tuning doc says the same and adds the cost of changing each. If the two ever disagree, **the
function is right.**

This librdkafka **rejects** the three idempotence-conflicting combinations (`acks=1`,
`retries=0`, `max.in.flight > 5`) loudly at construction — that was measured on the installed
library (client 2.15.1 / librdkafka 2.15.1), by constructing a client per combination, not read
from a doc. Full rationale, the effective-config dump procedure, and the `[GAP]`s are in
`docs/kafka-producer-tuning.md`.

**The key:** `f"{career_site_id}|{user_id_pseudo}"`, computed by the gateway
(`contracts/attributes.py: derive_kafka_key`) from the tenant the JWT named and the pseudonym the
encrypt stage just produced. **Set a raw key string; do not pre-hash it**, or the key is hashed twice.
One `(tenant, user)` pair therefore lands on one partition.

**You must order by `sequence`, not by partition.** Contract §6 says exactly what is and is not
guaranteed, and it is less than the original document claimed: `Settings.sticky_routing` exists and
compose sets `STICKY_ROUTING=1`, but **no code path reads the setting**, because there is no
consistent-hash layer between the listener and the uvicorn workers. Partition affinity is real;
single-producer ordering is only *usually* true.

**You must dedup on `(source, id)`.** The gateway never dedups across requests — a `503` + resend
puts the same pair on the topic twice by design, and `enable.idempotence` does not prevent it.
`contracts/ledger.py: dedup_key` is the helper.

**The DLQ shape, and the part you must not get wrong.** `career.events.dlq` carries a CloudEvent
(`type = com.careerpage.career.ingest-rejected`) whose `data.original_payload` is **one of two
shapes**, decided by `data.error_context.stage`:

- `"validate"` → the **plaintext request element**. This record **contains plaintext PII.**
- `"encrypt"` → the **encrypted** event.

**Treat `career.events.dlq` as a PII store when you set retention or access on it.** A
validate-stage record is the client's request as it arrived — `email`, `phone`, `name` and all — and
that is deliberate: the event was already judged invalid, so encrypting it is work on a dead record,
and redacting it would leave an operator holding something they cannot diagnose. What is true of
*every* record, at either stage, is that `data.error_context` never carries the offending value — the
`reason` is a code plus a JSON path, never the value, because the reason is written to a topic.

`app/dlq/envelope.py: dlq_data_to_ingress(data, target)` round-trips each shape to the struct it was
stored as. **A validate-stage record comes back as an `IngressEvent` and is encrypted exactly once on
re-injection. An encrypt-stage record comes back as a `CloudEvent` and must not be re-encrypted** —
that is a double-encryption bug. The DLQ key is the tenant `source`, not the derived user key.

**`python -m tools.verify` is your reconciliation oracle.** It reads the ledger plus both topics and
prints one scorecard. Exit codes are part of the contract: `0` pass, `1` mismatch, **`2` unverified**,
and on `2` **no scorecard is printed at all** — an unreadable ledger, an unreachable broker, or a
topic read that did not drain to every partition's end offsets each print one line and stop, because
a truncated view that looks balanced is worse than no tool. Note that the Cassandra dimension is
reported `skipped` and the pseudonym dimension is `skipped (no master secret)` unless a master secret
is supplied; neither is ever printed as a passing zero.

**Read the flags before you read the scorecard.** `--expect-duplicates` defaults to 0 but exists
because a gateway killed mid-flight makes the driver resend the same `id`s, which duplicates by
construction. The shipped `kill_gateway.sh` asserts `--expect-duplicates 0` because it resets both
topics first, and `tenant_flood.sh` **expects exit 1** because a shed tenant's batches are in the
ledger but were never accepted. A non-zero duplicate count is not automatically a bug, and a
non-zero expected count is not automatically fine.

**`application-abandoned` is synthesised by YOUR Flink job** on the watermark timeout
(`SPEC.txt:350`, 30-minute session window) — **never by us and never by the driver.** Both teams
emitting it would double-count the drop-off metric. The type is nonetheless in the published
`EVENT_TYPES` enum, because the client's "save and apply later" journey needs it to exist on the wire.

### Database — the field set is the whole story

**You receive,** per event, under `data.candidate`:

| Field | Form | Joinable? | Reversible? |
|---|---|---|---|
| `user_id_pseudo` | `HMAC-SHA256(mac_key, user_id)`, 64 hex chars | **Yes** — this is your user key | **No** |
| `email_hmac` | `HMAC-SHA256(mac_key, email)`, 64 hex chars | **Yes** — for equality grouping only | **No** |
| `email_enc`, `phone_enc`, `alternate_phone_enc`, `name_enc`, `gender_enc` | `"<keyversion>.<base64url(nonce‖ciphertext‖tag)>"` | No | Only with `enc_key` |
| `experience_status`, `years_of_experience`, `education_degree`, `education_branch` | **plaintext** | Yes | N/A |
| `user_id` (raw) | **never published** — not in any context attribute, not in the Kafka key, not in the ledger | — | — |

**You can join on the HMACs and you can never reverse them.** Given the master secret an attacker can
confirm a guess, not recover the value: a SHA-256 tag over a 32-byte secret key is not a lookup table.
That is the point — these are the only PII representation a downstream job holding **no key** can read.
No normalisation is applied, so case-fold an email **before** the HMAC if you want case-insensitive
grouping, or the group will split.

**Derive the keys yourself and they must match byte-for-byte** (`app/crypto/keys.py`, one HKDF extract
and two expands):

```
enc_key = HKDF-SHA256(ikm=master_secret, salt=career_site_id, info=b"enc")
mac_key = HKDF-SHA256(ikm=master_secret, salt=career_site_id, info=b"mac")
```

The master secret must be ≥ 32 bytes. `keyversion` is a plain-text prefix on every ciphertext
precisely so a consumer can select a key before reading a byte of payload.

**To read a plaintext PII value, use `POST /v1/decrypt`** (contract §2) — the body is
`{career_site_id, event, field}` for **one event and one field** (it is *not* a batch; an operator
asking for 500 fields is asking for an export, which is a different and differently-authorised
thing), gated by `X-Operator-Key`, rate-limited on its own 10/sec budget, and **every attempt is
audit-logged** — successes, denials and failures alike — with who and which `(source, id)`, never the
value. It only decrypts the five `*_enc` fields: `user_id_pseudo` and `email_hmac` are **not
decryptable**, they are HMACs, and asking for one is a `400 UNKNOWN_FIELD`. The plaintext comes back
in the response body and nowhere else, with `Cache-Control: no-store`.

**Tenant isolation is yours to enforce in the query.** No raw CQL: the DAL must inject `tenant_id`
into the `WHERE` clause (`SPEC.txt` §5C). Every event carries `source = /careers/<career_site_id>` and
`tenant` in the ledger.

## 3. Key derivation, in one place

```
client user_id  --HMAC-SHA256(mac_key, user_id)-->  data.candidate.user_id_pseudo
                                                      |
                              f"{tenant}|{pseudonym}"  +-->  Kafka message key
                              (derive_kafka_key)             hashed by consistent_random
```

`mac_key` is per tenant, so the same `user_id` under two tenants produces two unrelated pseudonyms —
that is intended, and it is why the derivation is not well defined across sources.

**The one trap, and it is a PII fact as well as a join trap.** `contracts/ledger.py`'s `user_pseudo`
field holds the **client's plaintext `user_id`**, *not* the topic's HMAC, and those two strings are
never equal. So the join is **not** `ledger.user_pseudo == topic.user_id_pseudo`. It is:

```
pseudonymize(derive_tenant_keys(master, salt=tenant).mac_key, ledger.user_pseudo)
    == topic.data.candidate.user_id_pseudo
```

which needs the master secret, and which is why `tools.verify` reports that dimension as `skipped`
without one. Joining the strings directly reports a total loss on a run where nothing was lost.

**The same fact, stated as a governance one: `ledger.jsonl` contains raw `user_id`s.** Not on either
Kafka topic, not in any context attribute, and not in the Kafka key — but in the ground-truth ledger,
in the field misleadingly named `user_pseudo`. Anyone retaining, copying or shipping that file is
handling a plaintext identifier column.

## 7. Open questions — things we could not resolve from the code

Each of these is a real gap, not a placeholder. None of them has been papered over in the contract.

1. **`event.schema.json` is unresolvable standalone.** `contracts/cloudevent.py: generate_schema_json`
   drops the `$defs` components msgspec returns. Fix is one line in a file this slice does not own.
   **Owner: whoever owns `contracts/cloudevent.py`.** Until then, code against the struct.
2. **No worker affinity is implemented.** `Settings.sticky_routing` reads `STICKY_ROUTING` and is
   read by nothing; there is no consistent-hash layer in front of the uvicorn workers. Partition
   affinity holds; single-producer ordering does not always. **Owner: whoever owns the ingress
   topology.** Until then `sequence` is mandatory for consumers, which is what the contract now says.
3. **The top 297 B of the ingress cap is admitted and then refused** for an event whose bulk is all
   encrypted payload. Measured, not estimated: the largest fully-encrypted ingress event that fits
   under the 64 KiB ceiling is **48,855 B** against a cap of **49,152 B**, and an event at the cap
   encrypts to 65,923 B — 387 B over. The cap was **not** lowered. It is a published contract value
   and changing it changes what clients may send, which is not a test's decision or a doc's; the
   measurement shows the post-encryption check catches the case rather than letting it onto the
   topic, so the constant is not unsafe — its top 297 B are simply unusable.
   **So this is yours to decide, not ours: either accept the dead zone, or change the cap, and
   publish whichever you choose.** **Owner: the three consumer teams**, UI most affected, because UI
   is the team that fills every candidate field. The number to argue from is in contract §2; the
   measurement that produces it is `python -m pytest app/test_config.py -s -q`.
4. **`app/ingest/__init__.py`'s module docstring still says "the DLQ carries the post-encryption
   event."** That is the claim this slice was asked to correct, and it is corrected in
   `app/dlq/envelope.py`, `app/ingest/pipeline.py` and contract §4 — but the package docstring was
   not this slice's file and still contradicts them. **Owner: whoever owns `app/ingest/__init__.py`.**
5. **The un-acked loss window is unmeasured.** §3 of the contract names the three bounds that shape it
   (`PRODUCER_QUEUE_MAXSIZE = 50,000`, `queue.buffering.max.kbytes = 64 MiB`,
   `_IN_FLIGHT_HIGH_WATER = 1,000`) and says the window's *size* is not established here. Note that
   two of those three caps are on different units over overlapping populations, so **the arithmetic
   will not tell you which binds first** — the gauges will.
6. **`SPEC.txt:143` points at "contracts/CONTRACT.md section 5"** for sticky routing. Ordering is
   §6; §5 is idempotency. The reference is stale in a file this slice does not own.
   **Owner: whoever owns `SPEC.txt`.**
7. **Every librdkafka *default* is unread.** The installed library exposes no resolved-config API, so
   for any value this repo does not set the honest answer is "librdkafka's default, and this
   repository has not read it." Marked `[GAP]` throughout `docs/kafka-producer-tuning.md`. Note also
   that `pyproject.toml` floors `confluent-kafka>=2.3`, so the host build and the compose build are
   not guaranteed to be the same librdkafka.
8. **The demo runs `apache/kafka:3.9.0`, RF 1, one node, no `min.insync.replicas`.** Client-side
   idempotence is fully in force and does its job; **nothing on the broker side is redundant.** If
   that disk goes, the events are gone and no client setting changes that.
9. **`python -m tools.observe` runs and exits 0 without printing anything.** `tools/observe.py`
   defines `main()` and has **no `if __name__ == "__main__":` block** — checked by running the module
   (zero bytes of output, exit 0) and by grepping the file. `tools/verify.py`, `driver/main.py`,
   `app/inspect.py` and `contracts/gen_schema.py` all have the guard; `observe.py` is the one that
   does not. So `make observe`, and the live-view step inside `make demo`, currently show nothing.
   **Owner: whoever owns `tools/`.** Not this slice's file, so it is listed rather than patched.
10. **`docs/kafka-producer-tuning.md` is stale on one row.** Its table and its "Finding" section say
   the shipped dict contains `compression.zstd.level` and is "rejected at construction … reported, not
   fixed". That was true when the doc was written; `app/config.py` has since been corrected to
   `compression.level`, which is the property librdkafka has. **Read the function, not that row** —
   contract §7 says the same, and the doc's own rule ("if this document and that function disagree,
   the function is right") covers it, but a reader who lands on the Finding first will be misled.
   **Owner: whoever owns `docs/kafka-producer-tuning.md`.**
11. **Three module docstrings in `app/ingest/` still carry the old DLQ claim**, not just the package
   one: `app/ingest/__init__.py` ("the DLQ carries the post-encryption event") and, inside
   `app/ingest/pipeline.py`, the module docstring's second bullet ("the record that reaches
   `career.events.raw` and the record that reaches `career.events.dlq` are both post-encryption … The
   DLQ is therefore not a second plaintext PII store"), `ingest_batch`'s own docstring (which still
   says the ingress cap makes `MAX_EVENT_BYTES` "unreachable by construction" — false for the
   encrypted-bulk shape, see §7 item 3), and the `DURABILITY_ACCEPTED_INTO_BUFFER` comment, which
   still says the loss window "is measured in T11" — a task number that no longer exists. What **is**
   corrected is `app/dlq/envelope.py`, `pipeline.py`'s stage-7 comment, and contract §4. None of those
   sites is this slice's file. **Owner: whoever owns `app/ingest/`.**
