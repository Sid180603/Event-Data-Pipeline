2. Multi-Tenancy Strategy in Apache Cassandra
In Cassandra, table metadata (Memtables, Bloom filters, SSTable indexes) overhead grows with every table created. A cluster generally suffers performance degradation past 200–500 total tables across all keyspaces.
Multi-Tenancy Pattern Matrix


Strategy
	Design
	Pros
	Cons
	Ideal For
	Discriminator Column (Shared Table)
	Include tenant_id as the primary component of the Partition Key.
	Max table efficiency; scales to millions of tenants; uniform cluster management.
	Requires software-level tenant isolation checks on every CQL query.
	SMB and Self-Serve Tenants.
	Keyspace per Tenant
	Separate Keyspace per tenant (e.g., company_a_career, company_b_career).
	Granular backup/restore; tenant-specific replication strategies.
	Hard limit on tenant count (~100–200 per cluster) due to metadata overhead.
	Tier-1 Enterprise / Dedicated SaaS.
	Hybrid Model (Recommended)
	Shared tables for Standard/SMB tenants; dedicated keyspaces or clusters for Enterprise.
	Balance between cost-efficiency and compliance isolation.
	High-growth enterprise platforms.

[ Frontend Event ]
      │

1. Ingestion Layer
* API Gateway: Validates tenant JWT tokens, extracts tenant_id, and enforces rate limits using a Token Bucket algorithm per tenant.
* Schema Validation: Ensures incoming JSON conforms to CloudEvents standards (specifying tenant_id, event_type, and timestamp).
2. Event Bus Design (Apache Kafka)
* Topic Naming Convention: career.events.raw (single topic, all event types). NOTE: an earlier draft of this
   spec proposed career.events.<environment>.<event_type> (a topic per event type). That is SUPERSEDED:
   splitting event types across topics breaks sessionization, which must order APPLICATION_STARTED ->
   STEP_COMPLETED -> SUBMITTED per (career_site_id, user_id, session_id). See contracts/CONTRACT.md section 6.
* Wire Format: CloudEvents 1.0 (CNCF Graduated), per SPEC.txt line 131 and contracts/CONTRACT.md.
* Partition Strategy: Message Key derived by the gateway as <career_site_id>|<user_id_pseudo>; the raw key
   string is set and Kafka's partitioner hashes it (do NOT pre-hash). A client-supplied partitionkey hint is
   ignored, and a disagreeing one is rejected.
   * Why: Guarantees strict order of operations for a specific user within a tenant while parallelizing
     processing across Kafka brokers. Requires sticky routing on (career_site_id, user_id) so one user maps
     to one producer; see contracts/CONTRACT.md section 5.
* Event type is the CloudEvents `type` attribute (reverse-DNS), not a topic.
* APPLICATION_ABANDONED is synthesised by the Flink sessionization job on the watermark timeout, NOT by the
   client or the event generator.
3. Stream Processing Layer (Apache Flink / Spark Streaming)
The stream processor handles distinct pipelines:
1. Short-path Pipeline (Cassandra Sink): Writes raw application records and job state changes directly to Cassandra.
2. Enrichment Pipeline:
   * Decouples heavy AI/ML resume parsing via worker queues.
   * Emits resume.parsed events back into Kafka once finished.
   * Updates parsed_skills in Cassandra asynchronously.
3. Analytics Aggregator Pipeline:
   * Computes tumbling/sliding window metrics (e.g., Job Views in last 1 hour, Drop-off rate at resume upload).
   * Writes materialized aggregated stats directly to Cassandra query tables.
5. Key Resilience & Operational Strategies
A. Preventing Hot Partition Issues
Large enterprise tenants generate exponentially higher traffic during hiring drives than SMBs.
* Bucketization: For high-volume log or audit tables, concatenate a temporal bucket (YYYY-MM or YYYY-MM-DD) to the partition key (e.g., PRIMARY KEY ((tenant_id, year_month), event_id)).
* Partition Size Boundary: Aim to keep Cassandra partitions under 100 MB or fewer than 100,000 rows.
B. Consistency Level Selection
Career pages are heavily write-heavy on applications and read-heavy on job descriptions.
* Application Submissions: LOCAL_QUORUM for both reads and writes to guarantee immediate consistency across local data centers without incurring cross-region network latency.
* Job Postings (Public Browsing): Write with LOCAL_QUORUM, Read with LOCAL_ONE backed by Redis/CDN caching at the API edge.
C. Tenant Isolation & Security
* Data Access Layer (DAL): Never allow raw CQL queries directly from microservices. All interactions must pass through an abstracted Data Access Layer that automatically injects tenant_id into the WHERE clause.
* Row-Level Security: Implement strict RBAC in application software to prevent tenant A from executing queries without their tenant_id bound to the partition key.

Key Processing Mechanics
1. Attribution & Source Identification:
   * API Gateway inspects client headers (X-Source-Type: WEB_APP | MOBILE_APP | THIRD_PARTY) and incoming payload attribution.referrer_type.
   * If referrer_type == "RECOMMENDATION", the pipeline links the event directly to the recommendation algorithm version ID.
2. Sessionization & Drop-off Detection (Apache Flink):
   * Flink groups events by (career_site_id, user_id, session_id) using a 30-minute session window.
   * If an APPLICATION_STARTED event is received without an explicit APPLICATION_SUBMITTED or APPLICATION_DRAFT_SAVED within the window, Flink automatically emits an APPLICATION_ABANDONED synthetic event with the last recorded step_number.
3. Autofill vs. Manual Field Detection:
   * Frontend DOM listeners send event flags indicating whether inputs were modified via standard keystrokes (MANUAL) or injected via parser payload mapping (RESUME_AUTOFILL).
4. Recommendation Workflow:
   * Upon receiving event_type == "APPLICATION_STARTED", a light consumer reads the candidate's education and experience_level to immediately trigger a vectorized query returning top-N similar job recommendations back to the client.
4. PII Security & Data Governance
Because candidate metadata contains Sensitive Personally Identifiable Information (PII) such as phone numbers, email addresses, and gender:
* Field-Level Encryption (FLE): Encrypt email, phone_number, and user_name at the API Gateway layer using AES-GCM before writing to Kafka or Cassandra.
* Separation of Analytics & PII: Keep analytical tables (application_funnel_sessions) pseudo-anonymized using user_id. Restrict access to candidate_profiles using Cassandra Role-Based Access Control (RBAC).

Data Lifecycle & Component Interaction
1. Ingestion & Origin Tracking
* Clients include a lightweight tracker SDK. When a user interacts with a job posting, the client attaches system context (source_channel: WEB_APP, MOBILE_APP, THIRD_PARTY), referrer path (SEARCH, RECOMMENDATION, THIRD_PARTY_WEBHOOK), and input method flags (MANUAL vs RESUME_AUTOFILL).
* API Gateway validates tenant authentication, applies field-level encryption (AES-GCM) to sensitive fields (email, phone_number, gender), and pushes the normalized event payload to Apache Kafka.
2. Event Partitioning & Stream Processing
* Kafka Partitioning: Messages are key-partitioned by hash(career_site_id + user_id). This guarantees chronological ordering for every action a user takes within a tenant portal.
* Apache Flink Processing:
   * Sessionization: Groups events into 30-minute sliding windows.
   * Drop-off Detection: If an APPLY_CLICKED event is received without a corresponding SUBMITTED or DRAFT_SAVED action within the window timeout, Flink synthesizes an APPLICATION_ABANDONED event marked with the last completed step number and time spent.
   * Autofill Ratio Metrics: Analyzes input completion tags to categorize whether an application was submitted via RESUME_AUTOFILL, MANUAL, or a HYBRID method.
3. Real-Time Recommendation Pipeline
* When an APPLY_CLICKED event reaches Kafka, the Recommendation Engine reads the candidate's profile vector (education degree/branch and experience level).
* It executes a nearest-neighbor vector search against the Vector DB (e.g., Qdrant/Milvus) to fetch similar job IDs, returning recommendation options to the client API in real time.
4. Cassandra Storage Layout
Writes from Flink and the Kafka Sink flow directly into partitioned Cassandra tables:
* candidate_profiles: Stores encrypted user metadata, gender, education, and years of experience.
* candidate_activity_counters: Atomic counters tracking total logins, views, started applications, and completed applications.
* application_funnel_sessions: Time-series log tracking step progression, time spent per step, and "Save and Apply Later" drafts.
* candidate_journey_attribution: Logs the entry path of every applicant (e.g., external webhook vs internal search vs recommendation engine).

User prompt: How is the event generator writing the data into the database, or say if the write request to database from queue failed, what should it do?
Response: In an event-driven architecture, writing data from a message queue (Kafka) via a stream processor (Flink / Custom Consumer) to Apache Cassandra requires a balance between high write throughput and strict failure resiliency.
1. How the Event Sink Writes Data to Cassandra
Writing to Cassandra requires a different approach than writing to traditional relational databases. Connections must avoid heavy single transactions and cross-partition locking.
┌─────────────────┐       ┌────────────────────────────────────────────────────────┐       ┌──────────────────┐
│  Kafka Topic    │──────►│ Consumer / Flink Sink Worker                           │──────►│ Cassandra Cluster│
│ (Partitioned)   │       │ - Prepared Statements                                  │       │ (Distributed)    │
└─────────────────┘       │ - Partition-Aware Grouping (Unlogged Batches)          │       └──────────────────┘
                         │ - Token-Aware Connection Pool                          │
                         └────────────────────────────────────────────────────────┘

A. Asynchronous Concurrent Writes & Connection Pooling
* Token-Aware Routing: The Cassandra client driver (e.g., DataStax Driver) maintains a topology map of the cluster. It routes write requests directly to the coordinator node holding the specific career_site_id partition, eliminating inter-node network hops.
* Prepared Statements: Statements like INSERT INTO application_funnel_sessions (...) are compiled once during startup. During writes, only the bound parameters are sent over the wire, saving CPU on both application and database nodes.
* Async I/O (executeAsync): Rather than blocking thread by thread, consumers fire asynchronous CQL queries concurrently using non-blocking Netty I/O worker threads.
B. Partition-Aware Batching
* Avoid Logged Batches: Standard multi-partition LOGGED BATCH statements in Cassandra introduce severe coordinator overhead and performance degradation.
* Partition-Grouped UNLOGGED BATCH: Events in memory are grouped strictly by (career_site_id, job_id). If multiple events belong to the same partition, they are flushed together in a single UNLOGGED BATCH. If they span multiple partitions, they are executed as concurrent asynchronous single-row writes.
2. What Happens When a Write to Cassandra Fails?
When a write fails (due to network blips, Cassandra node GC pauses, schema mismatches, or node failures), the pipeline executes a multi-tiered resilience strategy:

                         │  Execute Cassandra     │
                         │        Write           │

                                     │
                                     ▼
                            [ Write Successful? ]

                          YES                   NO
                          /                       \
                         ▼                         ▼
           ┌────────────────────────┐   ┌───────────────────────────────────┐

           │ (Acknowledge Message)  │   │ (WriteTimeout, Overloaded, Connection)
           └────────────────────────┘   └─────────────────┬─────────────────┘

                   ┌───────────────────┐          ┌────────────────────────────────┐

                                                  └────────────────────────────────┘

Step 1: Retry Strategy for Transient Errors
Transient errors include WriteTimeoutException, UnavailableException, or OverloadedException.
1. Driver-Level & Sink Retries: The consumer uses an Exponential Backoff with Jitter retry policy (e.g., initial wait 100ms, doubling up to 5 seconds with randomized delay to avoid thundering herd problems on recovering nodes).
2. Consistency Level Downgrade (Fallback): If writing at LOCAL_QUORUM fails due to a node going down, high-priority time-series events can fall back to LOCAL_ONE to preserve write availability, flagging the record for later reconciliation.
Step 2: Stream Backpressure & Offset Management
To prevent data loss, message offsets in Kafka must not be committed until Cassandra explicitly acknowledges the write.
1. At-Least-Once Delivery: The Kafka consumer fetches a batch of messages, writes them to Cassandra, and only then commits the offset back to Kafka.
2. Flink Checkpointing: In a Flink pipeline, state and Kafka offsets are committed atomically via two-phase commit checkpoints.
3. Backpressure Trigger: If Cassandra is overwhelmed and writes begin slowing down, the internal buffers in Flink/Consumer fill up. This automatically halts reading from Kafka, allowing Cassandra time to recover without dropping events.
Step 3: Handling Non-Transient / Poison Pill Events (Dead Letter Queue)
Non-transient errors (e.g., bad data types, invalid UUIDs, schema mismatches, or records exceeding maximum retry attempts) will never succeed no matter how many times they are retried. Blocking the consumer stream for these "poison pills" causes consumer lag.
1. Dead Letter Queue (DLQ) Routing: When retries expire or a non-retryable exception is caught, the consumer wraps the failed event with error metadata and publishes it to a dedicated Kafka topic: career.events.dlq.
2. DLQ Message Context:
{
 "original_payload": { ... },
 "error_context": {
   "exception_class": "InvalidQueryException",
   "error_message": "Column 'unknown_field' declared in CQL statement does not exist",
   "failed_at": "2026-09-30T14:52:00Z",
   "retry_count": 5,
   "original_topic": "career.events.raw",
   "original_partition": 3,
   "original_offset": 8849201
 }
}

3. Unblocking the Pipeline: Once routed to the DLQ, the pipeline commits the original message's offset in the main topic and proceeds to the next event.
4. DLQ Monitor & Replay Service: A dedicated alerting service notifies engineers of DLQ growth. Once schema fixes or code patches are deployed, a replay worker reads from career.events.dlq and re-injects events back into the main pipeline.
Step 4: Guaranteeing Idempotency on Retries
Because network timeouts can occur after Cassandra has written the data but before sending an ACK back to the client, retrying a write can result in executing the same CQL statement twice.
To ensure retries do not corrupt state or cause duplicate counts:
   1. Deterministic Primary Keys & TIMEUUID: Use client-side generated UUIDs/TIMEUUIDs (e.g., event_id or session_id) inside the primary key. Re-inserting the same row simply overwrites the exact cell idempotently without creating duplicates.
   2. Explicit Timestamps (USING TIMESTAMP): Every INSERT statement attaches the event's original source timestamp (USING TIMESTAMP <event_timestamp_micros>). If an out-of-order or duplicate retry arrives, Cassandra's Last-Write-Wins (LWW) conflict resolution guarantees that the write with the higher timestamp persists correctly.
   3. Separate Atomic Counters: Never mix status updates and counter updates in the same table. For metrics like total_job_views, route updates to a dedicated counter table in Cassandra or compute exact counts via stateful aggregation inside Flink before writing the result to Cassandra.
